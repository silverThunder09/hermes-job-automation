# 단일 공고 검토 산출물 빌드


## 목적과 경계

`build-case`는 [job-tailoring](../skills/job-tailoring/SKILL.md)의 **에이전트가 작성·대조한 입력**을 실제 등록 공고 조회, 필수조건·점수·숫자 토큰 확인, DOCX/PDF 생성, 로컬 검토 기록으로 연결합니다. 공고/회사 사이트 조사, PDF 내용 해석, 맞춤 글 작성과 사실성 판단을 CLI가 자동 수행하는 것은 아닙니다. 이 단계는 Hermes 작업 절차가 담당합니다.

- 유일한 앱 상태 저장소는 기존 Supabase PostgreSQL입니다. 기존 공고를 `read_only=True` 저장소의 GET으로 조회하며 공고·평가·지원 상태를 변경하지 않습니다.
- 결과 JSON과 서류는 비공개 로컬 산출물입니다. **DB 평가 저장 완료나 지원 완료가 아닙니다.** 로컬 파일은 대체 상태 DB가 아닙니다.
- 별도 모델 API 호출, Google/Telegram 전송, Storage/Drive 업로드, 지원 양식 조작, 제출, 삭제, 스케줄 등록은 하지 않습니다. `--execute`·`--write-state` 옵션도 없습니다.
- 원본 이력서/포트폴리오를 변경하지 않습니다. 포트폴리오만 있는 경우 신규 초안으로 표시하고 누락된 개인 정보를 예시 프로필로 채우지 않습니다.
- 기존 `run`/`finalize`의 동작은 바뀌지 않습니다. 이 두 명령은 `--execute` 없이도 상태 DB에 쓸 수 있으므로 혼동하지 마세요.

## 실행

설정된 환경에서 대상 체크아웃의 패키지를 사용합니다. 아래 경로는 사용자 비공개 입력/아직 없는 출력 폴더로 바꾸세요.

```bash
PYTHONPATH=src python -m hermes_job_automation.cli build-case \
  --file generated/company/posting/run/case-input.json \
  --output-dir generated/company/posting/run/build
```

`--output-dir`은 **존재하지 않는 새 폴더**여야 합니다. 이미 있는 폴더/서류는 덮어쓰거나 삭제하지 않습니다. 문서 생성 중 실패하면 부분 산출물이 남을 수 있으며, 이를 성공 결과로 해석하지 않습니다. 원래 폴더를 보존하고 원인을 해결한 후 별도 새 출력 폴더를 사용하세요.

## 입력 계약

`case-input.json`은 에이전트가 원문과 대조해서 작성하는 객체입니다. 기존 `finalize`용 `evaluations` 배열이나 수동 수집기의 `user_reviewed_manual` 입력 형식과 다릅니다. 에이전트 조사를 사용자 최종 검토 완료로 표시하지 마세요.

| 필드 | 의미 |
|---|---|
| `schema_version` | 정수 `1` |
| `posting_key` | 실제 Supabase에 등록된 정확한 공고 키 |
| `posting_snapshot` | 현재 웹에서 재확인한 `Posting` 필드. DB 공고와 플랫폼/ID/키/정규 URL/회사/제목이 일치해야 함 |
| `posting_observed_at` | timezone을 포함한 실제 브라우저 확인 시각 |
| `source` | `path`, SHA-256 `sha256`, `kind`(`portfolio` 또는 `resume`). 원본은 PDF/DOCX |
| `profile` | 원문에서 확인한 사실과 페이지 근거. 원본에 없는 사실을 넣지 않음 |
| `evaluation` | `technical_fit`(0~35), `work_fit`(0~30), `project_fit`(0~25), `preferred_qualifications`(0~10), 합계 `total`, `rationale`, `gaps`, `eligibility`, 실제 작성 `model` |
| `documents` | 검토용 `resume`, `cover_letter` 문자열 |
| `missing_information` | 본인 확인/보완이 필요한 항목의 문자열 배열 |

정수 점수에 문자열·실수·불리언을 사용하지 않습니다. `source.path` 상대경로는 입력 파일 위치 기준입니다. 파일 해시·입력 형식·숫자 토큰 검증 실패, 원본/입력과 출력 경로의 겹침, 기존 출력 폴더는 네트워크 조회와 출력 생성 전에 거부합니다. 등록 공고 부재나 식별자 불일치도 성공 산출물로 대체하지 않습니다.

`evaluation.eligibility`는 명시적인 `eligible`/`review`/`excluded` 문자열만 허용하며 빈 값·불리언 등을 검토 상태로 자동 변환하지 않습니다. DOCX는 기존 라이브러리로 OOXML 패키지를 열어 확인하고, PDF는 헤더·종결·cross-reference 위치의 기본 컨테이너 구조를 확인합니다. PDF 전체 구문·서명·페이지 렌더링의 완전한 검증은 아니므로 상류 단계의 실제 원문 열람·내용 대조를 생략할 수 없습니다. 생성 문서 두 종류 모두 원본 종류에 따른 신규/검토 초안 표시와 `최종 제출본 아님`을 자동으로 붙입니다.

관측 시각이 미래이거나 timezone이 없으면 입력 오류입니다. 관측 후 **24시간이 지난 입력**은 재확인이 필요한 보류 대상으로 처리합니다. 이는 이 빌드 입력의 오래된 공고 사용을 막기 위한 기준이며, 공고 7일 보관/삭제 정책이나 지원 기한을 바꾸는 기능이 아닙니다. 관측이 최근이어도 사이트의 조기 마감 가능성은 남으므로 제출 직전 재확인이 필요합니다.

## 판정과 출력

1. 입력·원본 해시·점수·숫자 토큰 확인.
2. 기존 Supabase에서 정확한 공고 GET 조회. 웹 재확인 snapshot과 등록 식별자를 대조. DB의 기존 검토 상태는 덮어쓰지 않음.
3. 웹 snapshot에 필수조건 판별을 재실행.
4. 필수조건 제외/검토 필요, 평가의 `eligibility` 불충족, 기준 점수 미달, 오래된 관측이면 문서를 생성하지 않고 보류 이유를 저장.
5. 조건이 충족되면 기존 문서 생성기로 이력서·자기소개서의 DOCX와 PDF를 생성. PDF는 DOCX 변환물이 아니라 같은 본문을 별도로 렌더링한 파일.
6. 원본 해시를 재확인하고 `review.json` 저장.

점수 기준은 설정의 `MINIMUM_SCORE`를 따릅니다. 점수는 작성 모델의 근거 기반 판단이지 합격 확률이나 회사의 평가가 아닙니다. 숫자 토큰 검사는 새로운 숫자의 유입을 막는 보조 수단이며 의미상 진실, 기여 범위, 측정 조건을 자동 증명하지 않습니다.

- `needs_information`: 검토용 문서는 만들었지만 학력·전화번호·재직 상세 등의 본인 확인이 남음.
- `ready_for_user_review`: 사용자 검토를 받을 수 있음. **사용자 승인/제출 가능 최종 확정과 다릅니다.**
- 보류: 생성하지 않은 문서를 생성했다고 표시하지 않고 이유를 남김.

`review.json`에는 공고 키/관측시각, 평가/근거, 남은 정보, 원본 전후 해시, 생성 경로와 실제 모델 출처를 남깁니다. CLI stdout은 문서 본문·프로필·연락처를 출력하지 않는 요약입니다. PDF 쪽수·한글 추출·잘림/겹침과 DOCX 내용을 별도 확인해야 문서 검토가 끝납니다.

## 개발·검증

- ADR 불필요: 기존 Python/CLI/문서 라이브러리와 승인된 Supabase GET 계약을 연결하며 새 서비스·주요 의존성·DB/권한·보관/삭제 정책을 도입하지 않습니다.
- 테스트: `tests/test_case_build.py`, 기존 문서·CLI·저장소 계약 및 전체 회귀. HTTP transcript 성공은 실제 Supabase 성공과 구분합니다.
- 실제 검증은 승인된 원본/공고로 명령을 실행하고, 생성물과 원본 해시 및 기존 DB 상태 불변을 직접 확인해야 합니다. fixture만으로 실사용 완료를 주장하지 않습니다.
- 이 흐름만으로 자동 공고 탐색, 무인 모델 인증, PC-off 예약, 실제 제출까지 완성됐다고 표현하지 않습니다.
