# 품질 게이트·이슈 대응·사람 승인 — 정책 초안

**상태: 훅 등 나머지 제안은 Proposed.** [ADR-0004](adr/0004-quality-gates-and-approvals.md)의 훅 구현/설치, Git 설정·원격 보호 변경은 결정/적용하지 않았습니다. 사용자가 별도로 명시 승인한 개발 PR의 이슈→리뷰→병합 및 결함 반복 규칙은 [PR 절차의 단일 원본](PR_AUTOMATION.md#review-loop)을 따릅니다. 이 부분 승인으로 나머지 제안이나 운영 권한을 확정하지 않습니다. 기존 비밀 보호·외부 변경 승인 경계는 유지합니다.

## 1. 커밋 훅 설계안

이 저장소는 Python 프로젝트입니다. 별도 Node 생태계를 추가하기보다 **기본 Git 훅 + 기존 Python**을 우선안으로 제안합니다. 아직 선택을 확정하거나 실행 파일을 만든 것은 아닙니다.

| 게이트 | 제안 검사 | 실행 경계 |
|---|---|---|
| `pre-commit` | staged diff 공백 오류, 개인정보/자격 증명/실행 DB 금지 경로, 고신뢰 비밀 패턴, staged Python/JSON 구문 | index에 올라간 정확한 내용 검사. 워킹트리와 다른 부분 스테이징도 검증. 자동 수정·자동 stage 없음 |
| `commit-msg` | 첫 줄 Conventional Commits 형식, 100자 제한 | 메시지를 읽기만 하고 자동 고치지 않음 |
| `pre-push` | 실제 push 대상 커밋의 회귀 테스트·구문 검사, main 직접 push 제한 | 현재 dirty working tree 검사로 대체하지 않음. 격리된 대상 snapshot 사용, 원격 DB 쓰기·개인문서 업로드 없음 |
| PR CI | 기존 테스트 및 PR 메타데이터 검사, 변경에 필요한 격리 SQL 검증 | head/base를 확인. local fixture/SQL/live 결과를 구분 |

- 비밀 검사는 모든 개인정보/키를 검출한다고 보장하지 않습니다. 결과에는 파일 경로와 규칙만 남기고 일치한 비밀 값은 출력하지 않습니다.
- 훅을 통과해도 이슈 실재 여부·ADR 타당성·원격 운영 정상·병합 승인을 대신하지 않습니다. 로컬 훅은 우회될 수 있어 CI/리뷰/원격 보호를 함께 사용합니다.
- 훅 실패 시 원인 수정과 재검증이 원칙입니다. `--no-verify`/무검사 우회는 사용자의 구체적 승인과 사유·누락 검사 보완이 필요하며 비밀/개인정보 반출은 허용하지 않습니다.
- 설치 전 기존 훅과 `core.hooksPath`를 확인합니다. 기존 훅을 덮어쓰지 않고 설치/해제 방법을 마련합니다. 저장소 설정은 여러 worktree에 영향을 줄 수 있으므로 적용 범위와 기존 값 보존을 사용자에게 확인합니다.
- 신규 formatter/linter/비밀 검사 도구가 필요해지면 의존성·Python 3.9 호환·설치/네트워크 비용을 새 ADR 또는 이 ADR 수정안에서 먼저 비교합니다. 아직 미도입인 도구를 실행했다고 주장하지 않습니다.

### 훅 구현 완료로 인정할 조건

실제 임시 Git 저장소에서 정상/실패 commit 및 push를 실행하고, 부분 스테이징·공백/한글 경로·비밀 출력 억제·실패 시 index/워킹트리 불변·정확한 push 대상·기존 훅 보존·설치/해제와 worktree 영향을 검증해야 합니다. 단순히 훅 파일이 존재하는 것으로 완료 처리하지 않습니다. 실제 프로젝트의 hook 활성화는 그다음 별도 승인 단계입니다.

## 2. 이슈 발견 시 대응

1. **관찰·분류:** 기대/실제 동작, 재현 입력, 버전/환경, 영향 범위를 확인합니다. 로그는 비밀 없이 최소한으로 남깁니다. 추측을 확정 원인으로 쓰지 않습니다.
2. **위험 제한:** 유출·손상·중복 제출 위험이 있으면 해당 작업의 추가 쓰기/자동 재시도를 중단하고 즉시 알립니다. 기존 데이터 삭제나 운영 설정 변경으로 임의 수습하지 않습니다.
3. **추적:** 기존 이슈/PR을 읽어 중복을 확인합니다. 권한이 없으면 로컬 이슈 초안을 준비합니다. 실제 이슈 게시·댓글·상태 변경은 승인 범위 안에서만 수행합니다. 키나 개인 서류를 공개/비공개 이슈에 붙이지 않습니다.
4. **처리:** 승인된 범위의 원인이 분명한 국소 버그는 재현 테스트 → 최소 수정 → 회귀 검증으로 처리합니다. 기능 확대·기술 선택·보안 정책 변경은 별도 이슈/ADR·사람의 결정으로 분리합니다.
5. **정체·실패:** 동일 가설로 실패를 반복하지 않습니다. 개발 PR의 누적 수정 횟수·재이슈·사람 승인 전환은 [승인된 반복 규칙](PR_AUTOMATION.md#review-loop)을 적용합니다. 불확실한 외부 쓰기는 재시도 횟수와 무관하게 즉시 재조회/사람 확인으로 전환합니다.
6. **종료:** 정확한 수정/검증 결과를 이슈·PR에 연결하고 최신 변경에서 회귀를 확인합니다. 로컬 테스트만으로 운영 이슈를 해결/종료했다고 말하지 않습니다. 외부 이슈 닫기와 병합은 승인 범위를 확인합니다.

| 심각도 초안 | 예시 | 처리 |
|---|---|---|
| P0 | 키/개인정보 노출, 실제 데이터 손실, 중복 지원 제출 위험 | 즉시 추가 위험 동작 중단·사람에게 알림. 임의 키 폐기·운영 DB 수정·증거 삭제 금지 |
| P1 | 핵심 저장/조회 실패, 지원 상태 변조, 동시성 보호 실패 | 해당 변경의 배포/병합 보류, 재현·원인·복구안 준비 후 검토 |
| P2 | 범위가 제한된 일반 버그 | 승인된 개발 범위 안에서 테스트와 최소 수정. 범위가 커지면 재승인 |
| P3 | 개선 제안·표현/경미한 사용성 | 로컬 backlog/이슈 초안. 현재 작업에 몰래 포함하지 않음 |

심각도는 영향 증거를 보고 조정합니다. P0/P1 및 완료 기준을 깨는 미해결 결함은 병합을 차단합니다. 단순히 P2/P3라고 낮게 분류해 요구사항 미충족을 허용하지 않습니다. 유예는 사용자의 위험 수용과 추적 항목을 기록합니다.

## 3. 사람의 승인 경계

이미 승인받은 작업의 동일 대상·동일 범위는 반복해서 묻지 않습니다. 새 대상/외부 효과/위험/비용/민감정보 범위로 바뀔 때만 새 승인을 받습니다.

| 작업 | 기준 |
|---|---|
| 요청 범위의 코드/문서 읽기, 공개 자료 확인, 격리된 로컬 테스트 | 추가 승인 없이 수행 가능. 비밀 전체 출력/무관한 계정 탐색은 제외 |
| 승인된 범위의 국소 수정·재현/회귀 테스트·로컬 이슈 초안 | 추가 승인 없이 진행. 범위 확대 시 중단·확인 |
| DB/프레임워크/모델 제공자/주요 의존성/실행 인프라/보안·보존 정책 선택 | Proposed ADR로 비교하고 사람의 결정 후 구현 |
| Git 훅 활성화·기존 훅 대체·여러 worktree에 영향 주는 Git 설정 | 적용 대상/변경값/복구안을 알리고 명시적 승인 |
| 커밋·push·실제 이슈/PR 게시·댓글/상태 변경 | 저장소/브랜치/대상 작업을 정한 승인. 로컬 수정 권한에서 추정하지 않음 |
| PR 병합·ruleset/branch protection·자동 병합 설정·force-push/이력 재작성 | 구체적인 별도 승인. 테스트/AI 리뷰는 사람 승인 아님 |
| 원격 DB schema/데이터 쓰기·마이그레이션 | 정확한 프로젝트/SQL/데이터 범위를 승인. 이미 승인한 공개 샘플 검증 등은 반복 요청하지 않음 |
| 기존 데이터를 지우는 정리·파일 5일 삭제·DB 이관·backend 기본 전환 | 데이터/환경별 범위와 보존·복구 방법 확인 후 승인. 단순 연결 승인을 삭제 승인으로 확대하지 않음 |
| 개인 문서 업로드·새 처리 경로/제공자로 전송 | 자료·목적·수신처·보관/접근 범위 확인 후 승인 |
| 예약 실행 활성화·유료 자원·과금 설정·외부 전송 알림 | 일정/대상/예산·중단 조건 등 영향 범위를 정한 명시적 승인 |
| 로그인/2FA/결제·권한 동의 | 사용자가 안전한 인증 흐름에서 처리. 비밀번호/코드/키를 채팅에 요구하지 않음 |

사이트의 접근 통제·CAPTCHA 우회, 원본 경험/성과 날조, 비밀을 로그/커밋에 넣는 행위는 승인 요청으로 정당화하지 않습니다.

승인 근거는 사용자 메시지와 대상/범위/허용 작업을 기록합니다. 리뷰·배포 대상이 달라지거나 위험이 커지면 영향받는 검증/승인을 갱신합니다. 시간 만료가 필요한 지원/계정 작업은 승인 유효기간을 명시합니다.

## 4. 완료 보고 규칙

**제안/문서 작성 → 코드 구현 → 로컬 검증 → 실제 설치 → 원격 게시/보호 → 운영 검증**을 따로 보고합니다. 한 단계의 성공을 다음 단계 완료로 표현하지 않습니다. 훅 설계가 문서에 있어도 설치된 것이 아니며, 정책 CI 파일이 있어도 원격 병합 차단이 설정된 것은 아닙니다.
