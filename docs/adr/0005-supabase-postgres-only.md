# ADR-0005: Supabase PostgreSQL 단일 상태 저장소로 통일

- 기록일: 2026-11-07
- 결정 상태: Accepted
- 승인 근거: 사용자가 확인 질문에서 **“Supabase PostgreSQL로 통일하고 SQLite 제거”**를 선택함
- 구현 상태: `feature/supabase-state-store`에서 단일화 완료. 앱의 SQLite 구현/기본값/선택 경로를 제거하고 로컬 backend 설정을 `supabase`로 전환
- 검증 상태: 2026-11-07 독립 재실행 78개 테스트 통과(실제 격리 PostgreSQL 11개 포함). backend override 없이 live Supabase health·공개 샘플 저장/조회·중복/상태 보존·실행 기록 재조회 통과. 기존 DB/서류 5개 해시 동일 확인
- 검증 증거: 개인 환경의 비공개 로컬 기록으로 보존. 공개 문서에서는 개인 경로·실행 레코드 식별자를 생략. 이 기록은 작업 시점 검증이며 이후 코드/환경 변경은 재검증 필요
- 이번 문서 PR 범위: 저장소 전환 소스는 포함하지 않음. 위 결과는 별도 기능 작업의 개인환경 검증 기록이며 이 PR/main의 배포 완료를 뜻하지 않음
- 대체하는 결정: ADR-0002 중 SQLite 공존/기본값 유지 정책. Supabase 선택과 기존 보안 경계는 유지
- 연결 이슈/PR: 문서 PR 발행은 승인됨. 초기 규칙 도입 PR 본문에서 추적하며 기능 구현 코드의 게시·병합은 별도 범위

## 요구사항과 대안

기존 설명에서 코드 기본 SQLite, Supabase 공유 저장소, SQL 테스트 전용 PostgreSQL이 섞여 혼란을 만들었습니다. 사용자는 단일 DB 체계를 요청했고, 두 구성 중 Supabase PostgreSQL 유지와 SQLite 제거를 명시적으로 선택했습니다.

- SQLite/Supabase 공존: 오프라인 실행이 쉽지만 설정/데이터가 갈라지고 사용자가 실제 DB를 혼동하기 쉬움.
- Supabase PostgreSQL 단일 저장소: 로컬과 클라우드에서 같은 저장 동작을 사용하며 구성 설명이 단순해짐. 네트워크와 자격 증명이 필요함.
- Supabase 없는 별도 PostgreSQL 서버: 직접 운영·접근/백업/비용 관리가 필요하며 사용자가 선택하지 않음.

## 결정

1. 앱 상태 저장은 Supabase PostgreSQL만 사용합니다. 기존 PostgREST adapter와 SQL/RPC, 서비스 키 보안 방식을 유지하며 새 DB 서버나 드라이버를 추가하지 않습니다.
2. 앱 코드의 SQLite adapter, 기본값, 초기화/파일 생성/선택 경로를 제거합니다. 명시적인 `sqlite` 설정은 원격 DB로 조용히 바꾸지 않고 설정 오류로 안내합니다.
3. 미지정 backend의 기본값은 `supabase`로 합니다. 자격 증명이 없으면 실제 저장 동작은 실패하고, 로컬 DB를 만들거나 다른 저장소로 우회하지 않습니다.
4. 사용자가 승인한 전환으로 로컬 `.env`의 backend 선택 값만 `supabase`로 변경합니다. 다른 자격 증명/사용자 설정은 보존하며 비밀 값은 출력하지 않습니다.
5. 테스트도 SQLite 저장소에 의존하지 않습니다. 로컬 HTTP 계약 fixture와 필요 시 격리된 실제 PostgreSQL로 검증합니다. fixture/테스트 더블은 운영 저장소 구현이나 실제 Supabase 성공의 대체물이 아닙니다.
6. 기존 SQLite 파일·원본 포트폴리오·생성 서류는 보존합니다. 데이터를 자동 이관하거나 삭제하지 않습니다. 이전 파일은 보관용이며 앱 실행 시 읽거나 쓰지 않습니다.

## 영향·보안·범위

오프라인 상태 저장 기능은 사라집니다. 네트워크 장애나 잘못된 원격 설정은 명확히 실패합니다. Supabase 무료 한도·가용성·비용은 그대로 관리해야 합니다.

기존 원격 schema/데이터를 삭제하거나 새 테이블을 임의 생성하지 않습니다. 개인 문서 업로드·파일 만료 삭제·예약 가동·실제 지원·GitHub 게시·Git 훅 활성화는 이 결정 범위가 아닙니다. 로컬 PostgreSQL은 SQL 테스트 전용이며 별도 실사용 DB 서버를 설치하는 선택이 아닙니다.

## 완료 기준

- 앱 소스에 SQLite import/연결/초기화/선택 코드가 없음.
- 기본/명시적 Supabase 설정은 정상이며 sqlite/잘못된 backend는 명확히 거부.
- 테스트는 자격 증명 없이 격리 실행 가능하고, 실제 PostgreSQL의 중복·동시성·상태 보존 검증을 유지.
- 기존 DB/원본 파일의 해시가 작업 전후 동일함을 확인.
- backend 강제 override 없이 실제 로컬 설정으로 `state-health`와 승인된 공개 샘플 `state-smoke --explicit-write`를 실행하고 저장 레코드를 재조회.
- 문서에서 현재 단일 저장소, 기존 파일 보관, 테스트 전용 PostgreSQL을 구분. 구현/로컬 테스트/live 검증 상태를 나눠 보고.

## 재검토·복구

오프라인 요구가 새로 생기거나 비용/가용성이 요구와 맞지 않으면 새 ADR로 대안을 검토합니다. 보관한 SQLite 파일을 자동 활성화하지 않습니다. 실패 시 추가 쓰기를 중단하고 코드를 이전 버전으로 복구하거나 전진 수정하되, 데이터 이관/삭제는 별도 승인으로 다룹니다.
