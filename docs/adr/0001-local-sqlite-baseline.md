# ADR-0001: 초기 로컬 상태 저장소의 SQLite 사용 — 사후 기록

- 기록일: 2026-11-07
- 결정 상태: Historical
- 구현 상태: 기존 코드에 구현됨
- 검증/운영 상태: 로컬 사용 경로 존재. 클라우드 공유 적합성을 입증한 것은 아님
- 연결: 규칙 도입 전 구현의 사후 정리; 가짜 과거 이슈/승인을 부여하지 않음
- 후속 결정: [ADR-0002](0002-shared-supabase-state.md)
- 추가 후속: [ADR-0005](0005-supabase-postgres-only.md)에서 SQLite 공존을 종료하고 Supabase PostgreSQL 단일화를 승인. 아래 내용은 초기 구조의 회고이며 현행 backend 지시가 아님

## 배경과 확인한 사실

기존 `src/hermes_job_automation/state.py`는 Python 내장 `sqlite3`로 상태 파일을 열고 트랜잭션, unique 제약, 실행/공고/지원 시도 기록을 처리합니다. 코드 기본 backend도 SQLite입니다. 최초 개발 당시의 ADR은 없으므로 아래는 현재 구조에 근거한 설명입니다. 사전에 여러 DB의 성능·비용을 측정해 선정했다고 주장하지 않습니다.

## 이 구조에서 얻는 장점

- 별도 DB 서버·계정·네트워크 연결 없이 로컬에서 시작할 수 있습니다.
- Python 내장 기능이라 DB 드라이버를 추가하지 않아도 됩니다.
- JSON 파일만 쓰는 것과 달리 고유 제약·트랜잭션으로 중복 저장과 지원 시도 상태를 관리할 수 있습니다.
- 로컬 테스트와 소규모 단일 호스트 MVP를 단순하게 만들 수 있습니다. 규모 적합성은 가정이지 부하 측정 결론은 아닙니다.

## 현재 관점의 대안과 한계

- 로컬 PostgreSQL: 서버 운영이 추가되며 PC가 꺼지면 접근할 수 없다는 문제는 그대로입니다.
- Supabase 같은 원격 PostgreSQL: 공유 접근에 맞지만 인증·네트워크·권한·무료 한도·이관을 관리해야 합니다.
- SQLite 파일의 Drive 동기화: DB 서버가 아니므로 동시 수정·덮어쓰기·일관성 조정이 필요합니다.

이 비교는 **현재 회고에서 정리한 것**이지 당시 검토 증거가 아닙니다. SQLite가 가장 빠르거나 보안상 가장 안전하다는 결론도 아닙니다.

## 요구사항 변화와 후속 결정

사용자는 로컬 개발을 유지하면서 PC가 꺼진 새벽에도 수집하고, 로컬·클라우드가 같은 상태를 조회하기를 원했습니다. 개인 PC의 SQLite 파일을 공유 원본으로 삼는 것은 이 요구와 맞지 않습니다. 공유 상태는 ADR-0002로 다루며 SQLite는 로컬 기본/테스트 경로로 유지합니다. Supabase 실패를 숨기는 자동 fallback으로 쓰지 않습니다.

기존 SQLite 데이터는 자동 삭제하거나 자동 이관하지 않습니다. 공유 저장소의 실제 검증과 명시적인 backend 선택을 별도로 확인합니다.
