# ADR-0011: 클라우드 수집과 원격 Supabase 저장 작업의 분리

- 기록일: 2026-11-15
- 결정 상태: **Accepted — 실행 경로·격리 및 조건부 1회 검증 범위**
- 구현/배포/검증: **미구현·미배포**. 별도 시험 브랜치에서 단건 원격 MCP 읽기만 확인했으며 검색·다건 저장·예약은 미검증.
- 연결 이슈: [#27](https://github.com/silverThunder09/hermes-job-automation/issues/27)
- 상위 결정: [ADR-0006](0006-actions-batch-boundary.md)의 실행·공개 개발/비공개 운영 경계를 구체화한다. 모델 인증·보존 제안을 승인하거나 대체하지 않는다.

## 수집 경로

| 시작 조건 | 선택한 경로 | 공통 결과 |
|---|---|---|
| PC-on | 로컬에서 클라우드 브라우저/MCP 작업을 시작 | 기존 Supabase 저장·중복 처리·정확한 재조회 |
| PC-off | GitHub Actions 예약 작업이 클라우드 실행을 시작 | 같은 Supabase를 공유하며 로컬 PC에 의존하지 않음 |

이 표는 승인된 목표 구조이며 가동 완료 표가 아니다. PC-off 목표 시각은 **04:00 Asia/Seoul**, 실제 예약 등록·활성화는 수동 원격 검증 후 별도 승인 대상이다. GitHub 예약은 지연·누락될 수 있어 정각 시작을 보장하지 않는다.

사람인 공식 API 경로는 이번 운영 선택지와 필수 조건에서 **폐기**했다. 이용 승인·access-key를 다시 요구하거나, API가 없다는 이유로 선택한 클라우드 브라우저 경로를 불가능하다고 판정하지 않는다. 기존 Python API 코드·설정/키의 삭제나 비활성화는 이 문서 변경에 포함되지 않는다. `sources`와 기존 `run`은 아직 그 Python 수집기를 실행할 수 있으므로 새 클라우드 수집 명령으로 안내하지 않는다.

기존 collector의 `manual_only`/`approval_required` 결과는 기존 구현의 상태이지 선택한 클라우드 브라우저/MCP 경로를 실행한 결과가 아니다. 실행 호스트 선택, 페이지 공개 열람, 플랫폼 자동 수집 허용, 사용자 저장 승인, 실제 저장 성공은 서로 다른 관문이다. [플랫폼 정책](../PLATFORM_ACCESS.md)의 접근 제어·CAPTCHA·로그인 우회 금지와 정기 수집 허용 확인을 유지한다.

## 승인 범위와 격리

1. 비공개 운영 저장소 `silverThunder09/hermes-job-automation-ops`를 만들고, 기존 업무 상태 설정 `SUPABASE_URL`·`SUPABASE_SECRET_KEY`·`SUPABASE_STORAGE_BUCKET`만 repository Secrets에 등록하는 범위를 승인했다. 공개 개발 저장소의 공개 범위와 main을 운영 자격 증명 보관소로 바꾸지 않는다. 키 값은 채팅·인자·로그·Git에 기록하지 않는다.
2. collection과 storage를 서로 다른 GitHub-hosted job으로 분리한다. collection의 브라우저/MCP는 DB 키를 받지 않는다. storage의 신뢰하는 단일 writer 단계만 키를 받으며 브라우저나 모델을 실행하지 않는다. 별도 job은 비공개 저장소의 검토되지 않은 코드를 안전하게 만드는 수단이 아니다.
3. 검토한 소스 commit을 고정한다. 임의 revision/URL 또는 수집 산출물 안의 명령을 자격 증명과 함께 실행하지 않는다. writer는 크기·스키마·건수·URL/ID·UTC 수집 시각·출처를 검증한 JSON 데이터만 처리한다.
4. 이번 검증은 **최대 10개 공고, 유한한 1회**로 제한한다. Java **또는** Spring을 별도로 검색하고 합집합으로 중복 제거한다. 모집 중·학력무관/고졸·서울/경기/인천·정규직/인턴·신입 또는 유급 백엔드 경력 0년 조건의 출처를 확인한다. 미확인·충돌을 적합으로 채우지 않는다.
5. agent 조사 출처와 사용자 검토 대기를 보존하며 `user_reviewed_manual`로 위장하지 않는다. 기존 store의 원자적 `save_posting`을 사용하고 기존 공고/적격성/평가/지원 상태·메모를 보존한다. 새 샘플·평가·지원 상태를 만들지 않는다.

## 비용·보안과 중단 조건

기존 Supabase 서버 secret은 넓은 권한을 가진다. 비공개 runner 제공은 새 신뢰 경계이며 새 키 하나가 최소권한 DB 역할을 만드는 것은 아니다. 별도 제한 역할/RPC/ingress는 추가 설계·운영 변경이다. [상태 저장소](../SUPABASE_STATE.md)의 HTTPS·redirect 거부·오류 비밀 보호 계약을 유지한다.

계정의 포함 실행량·초과과금 차단, Supabase 비용/용량 및 접근 범위를 가동 전에 확인한다. 계정 과금 화면·키·실행 원문은 공개 문서에 싣지 않는다. 무료 실행이나 무제한 용량을 단정하지 않으며 새 유료 서비스·카드·과금 한도 변경은 하지 않는다. 접근 차단·CAPTCHA·로그인 또는 허용 범위 불명확 시 중단하고, 단건 읽기 성공을 반복 수집 허가로 확대하지 않는다.

## 검증과 완료 기준

- [단건 원격 시험 #26](https://github.com/silverThunder09/hermes-job-automation/issues/26)은 GitHub-hosted Linux의 실제 Playwright MCP/Chromium 공개 공고 읽기 증거다. 모델 호출·DB 쓰기가 없었고, 전체 검색·저장 성공 증거는 아니다. 상시 Hermes Cloud 인스턴스나 유료 브라우저 서비스 도입을 뜻하지 않는다.
- 새 원격 소비자에서 실제 health/대상과 private 설정을 확인한다. Secret 이름·갱신 메타데이터 재조회는 값의 재조회가 아니며 소비자의 실제 성공으로 검증한다.
- collection에 DB 키가 없고 storage가 고정 코드만 실행하는지 확인한다. 로컬 fixture, 격리 SQL 및 실제 원격 서비스를 구분한다.
- **원격 검색·수집 → 원격 기존 Supabase 저장 → exact read-back**이 성공해야 PC-off 저장 완료다. 로컬 파일·실행 기록만 저장한 결과로 대체하지 않는다.
- 동일 데이터 재저장의 신규/중복 판정과 기존 상태·메모 보존을 정확한 canonical 행으로 확인한다. 불확실한 쓰기는 식별자로 재조회한 후 조정하며 무조건 재시도하지 않는다.

## 제외 범위와 문서 통합

예약 등록·활성화, 실제 지원/제출, Google/Telegram, 개인 파일 업로드, 삭제·보존 변경, 운영 SQL/권한 변경, 모델 인증 이전은 **별도 승인** 대상이다. 인증 lab·미병합 코드·보존 제안을 이 승인에 섞지 않는다.

사용자는 조건부 1회 원격 저장 검증과 이 문서의 main 통합을 승인했다. 문서 병합은 위 동작을 구현하거나 가동하지 않으며 다른 코드 PR의 병합을 승인하지 않는다. 후속 구현은 이미 승인한 범위에서 계속하되 새로운 정책·권한·비용이나 불확실한 외부 쓰기 경계에서 멈춘다.
