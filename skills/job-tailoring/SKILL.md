# 공고별 이력서 수정과 검토

이 스킬은 Hermes가 도구로 수행하는 절차다. Python의 기존 일괄 평가 파이프라인에 회사 사이트 분석·원본 이력서 편집이 자동 연결되었다는 뜻은 아니다. 실제 제출과 외부 업로드는 이 작업에 포함하지 않는다.

## 시작 조건

- 사용자에게 받은 공고 URL·공고 캡처/PDF와 원본 이력서를 확인한다. 첨부 파일은 로컬 경로로 읽을 수 있다.
- 포트폴리오만 있다면 프로젝트 근거 자료로 등록한다. 포트폴리오에 없는 학력·재직기간·직함·연락처를 예시 프로필에서 가져와 사실처럼 채우지 않는다. 원본 이력서 수정인지 신규 이력서 초안인지 구분한다.
- 원본을 덮어쓰지 않는다. 원본 경로와 SHA-256을 기록하고 작업 후 해시가 동일한지 확인한다.
- docs/PLATFORM_ACCESS.md를 따른다. 지정 URL을 사용자가 제공했다는 이유만으로 사이트 전체의 자동 반복 수집까지 허가된 것으로 간주하지 않는다.

## 1. 공고 분석: DOM 텍스트 + 이미지

1. 실제 브라우저로 지정 공고를 연다. 페이지 URL, 확인 시각, 접수 상태를 기록한다. 로그인·추가 인증·접근 제한은 우회하지 않는다.
2. 제목·회사·직무·업무·필수·우대·학력·경력·지역·고용형태·마감을 각각 원문 근거와 함께 추출한다. 필수와 우대를 섞지 않는다.
3. 텍스트가 있어도 이미지형 상세 공고가 따로 있는지 확인한다. 원본 이미지나 공고 영역 캡처를 확보하고 위치·이미지 해시를 기록한다. 장식 이미지와 공고 본문 이미지를 구분한다.
4. 저장된 이미지에는 프로젝트의 `ocr-image` 명령을 사용한다. 텍스트 PDF는 텍스트 레이어부터 읽고, 이미지형 페이지·도표는 별도로 확인한다.
5. Windows 로컬 OCR 출력은 항상 `requires_review=true`다. 신뢰도 점수가 없으며 이미지와 대조하기 전에는 검증된 사실이 아니다. 날짜·숫자·학력·경력·회사명은 확대 원본과 대조한다. 원시 OCR과 정정문을 따로 보존한다.
6. 긴 이미지는 OCR 최대 크기 오류가 발생할 수 있다. 원본을 보존하고 겹침 영역을 둔 조각으로 분리한 뒤 조각 좌표를 기록한다. 축소로 작은 한글이 사라지거나 하단이 잘린 결과를 전체 추출이라고 보고하지 않는다.
7. 연결 실패 시 바로 사용자에게 캡처를 요구하지 않는다. 먼저 원본 공고 ID를 보존한 채 검색어를 바꿔 검색하고, 검색 결과의 동일 ID 공개 페이지와 회사 공식 채용 페이지를 찾는다. 한 URL/브라우저 도구의 실패와 공고 자체의 접근 불가를 구분하며 공개 HTML·검색·정식 대체 페이지를 교차 확인한다. 공고 ID나 URL 검색어만으로 회사와 요건을 추측하거나 다른 공고의 경력·학력을 합치지 않는다. 이 경로들도 실패했을 때만 `blocked`/`review`를 기록하고 전체 캡처/PDF를 요청한다. OCR 모호함도 원본과 대조되지 않으면 확인 필요로 남긴다.

## 2. 회사 공식 사이트 분석

- 공고에 링크된 공식 도메인을 우선한다. 없으면 회사명·사업내용·소재지 등을 대조해 동일 법인의 공식 사이트인지 확인한다.
- 제품/서비스, 고객, 개발팀/기술 관련 공개 정보, 채용 안내 중 이 직무와 관련된 부분만 읽고 URL과 근거를 기록한다.
- 사이트가 없거나 연결 실패·회사 동일성이 불명확하면 건너뛰고 이유를 적는다. 찾지 못한 것을 '사이트가 존재하지 않음'으로 단정하지 않는다.
- 회사 소개는 회사에 대한 근거일 뿐 지원자의 경험 근거가 아니다. 공식 사이트 사실과 해석을 분리한다.

## 3. 수정 전 필수조건 확인

- 명시된 학력·경력·마감 등 변경 불가능한 필수조건을 먼저 확인한다. 맞지 않으면 제외/확인 필요 상태로 저장하고 이력서로 조건을 충족한 것처럼 꾸미지 않는다.
- 기존 eligibility.py는 고정 문자열 필터라 우대·부정문을 오판할 수 있다. 원문과 프로그램 판정이 다르면 충돌을 기록하고 사람 확인을 요청한다. 조용히 판정을 우회하지 않는다.
- 이 단계는 낭비를 막는 사전 확인이며, 최종 적합도·문서 품질 평가는 수정 이후 별도로 한다.

## 4. 이력서 수정

- 원본 이력서/포트폴리오의 사실과 페이지를 근거 목록으로 만든다. 링크가 달려 있어도 실제로 열어 검증하기 전에는 '문서 기재 사실'과 '독립 검증 사실'을 구분한다.
- 공고 요구사항 → 지원자 근거 → 반영할 문단을 연결한다. 자기소개, 기술 순서, 프로젝트 순서와 설명을 직무에 맞게 재배치·요약·명확화한다.
- 없는 기술·직장·성과·수치를 추가하지 않는다. 프로젝트 구현을 유급 재직 경험이나 운영 실적으로 바꾸지 않는다. 포트폴리오의 검증 한계와 측정 조건을 보존한다.
- 특히 서로 다른 부하 캠페인/release 관측값을 동일 조건 전후 실험이나 일반적인 성능 보장으로 바꾸지 않는다. 100%였던 1차와 99.9%였던 재측정을 섞지 않는다. 코드/설정 확인만 된 배포를 실제 AWS 전체 성공으로 표현하지 않는다.
- DOCX 입력은 복사본에 python-docx/Office 스킬로 편집한다. PDF 입력은 텍스트·시각 내용을 근거로 별도 편집본을 만들고 원본 레이아웃 보존을 약속하지 않는다.
- 포트폴리오만으로 신규 이력서를 만들 때 누락된 학력·근무 이력은 '확인 필요'로 남긴다. 최종 제출본으로 표시하지 않는다.
- 변경마다 원문, 수정문, 이유, 공고 근거, 지원자 근거를 남긴다.

## 5. 수정 후 판단

가능하면 수정 단계와 분리된 검토 패스로 확인한다. 같은 모델의 재검토를 독립적인 사실 검증으로 과장하지 않는다.

- 직무 적합도: 기술 35, 업무 30, 프로젝트 25, 우대 10. 각 점수에 공고 근거와 지원자 근거를 명시한다.
- 사실성: 추가·강화된 주장과 수치, 날짜, 기여 범위, 미검증 사항을 대조한다. 단순 숫자 토큰 검사만으로 진위를 보증하지 않는다.
- 문서 품질: 핵심 경험 노출, 중복/과장/모호한 표현, PDF 잘림·표/그림 누락을 확인한다.
- 결과는 `ready_for_user_review`, `needs_information`, `excluded` 중 하나다. 최종 사용자 승인을 자동으로 부여하거나 지원 완료로 기록하지 않는다.

## 6. 저장

프로젝트 내부 `generated/<회사>/<공고ID>/<고유한-실행ID>/`에 원본과 겹치지 않는 새 경로를 만든다.

- `sources.json`: URL·확인 시각·원본 경로/해시·페이지·OCR 방식·접근 실패/생략 이유
- `posting-analysis.md`: 공고 필수·우대·업무 분석과 원문 근거
- `company-analysis.md`: 공식 회사 사이트 분석 또는 생략 이유
- 수정본 DOCX 및 가능하면 렌더링 확인한 PDF (원본과 별개)
- `changes.md`: 문단별 변경 전후·변경 이유·근거
- `review.json`: 최종 상태·항목별 점수·사실성 검토·남은 질문·실제 사용 모델

공고를 읽지 못했으면 `blocked`/`needs_information` 결과만 남기고 회사별 수정본을 만들어낸 것으로 보고하지 않는다. 기존 finalize는 별도 스키마와 DB 공고 등록을 요구하므로 이 폴더를 그대로 finalize 입력으로 전달하지 않는다.

## 로컬 OCR 실행

프로젝트 루트의 PowerShell 예:

```powershell
$env:PYTHONPATH = Join-Path (Get-Location) 'src'
$env:PYTHONUTF8 = '1'
& '.\work\runtime\.venv\Scripts\python.exe' -m hermes_job_automation.cli ocr-image --file '.\공고.png' --language ko --output '.\data\새로운-공고-ocr.json'
```

Windows 10/11의 한국어 OCR 언어 기능이 필요하다. 결과 파일이 이미 있으면 덮어쓰지 않고 실패한다. 이 명령은 사이트 방문·이미지 다운로드·회사 분석·이력서 수정·지원서 제출을 자동 수행하지 않는다. 이미지와 텍스트는 OCR 처리를 위해 외부로 전송하지 않는다. PDF 렌더링은 별도 PDF 스킬을 사용한다.
